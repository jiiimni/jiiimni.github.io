1. 프로젝트 소개

5인 팀으로 공연 예매, 좌석 선점, 결제, 쿠폰과 실시간 알림 기능을 제공하는 티켓팅 플랫폼 백엔드를 구현했습니다. 예매·결제 도메인을 담당해 웹훅 검증, 예매 확정 로직 분리, 쿠폰 상태 전이 개선과 Redis 기반 동시성 제어 흐름을 맡았습니다.

공개된 웹훅 주소로 위조 요청이 들어오는 경우와 결제 실패 후 쿠폰이 돌아오지 않는 경우를 확인하고, 요청 검증과 쿠폰 복구 흐름을 수정했습니다.

2. 담당 역할

결제 웹훅 검증

HandlerInterceptor에서 서명을 검증하고 주문 금액과 PG 결제 금액을 비교했습니다.

쿠폰 상태 전이

HOLD, USED, AVAILABLE 3단계로 선점·확정·복구 흐름을 재설계했습니다.

예매 확정

결제 결과에 따른 예매 확정 책임과 트랜잭션 경계를 분리했습니다.

동시성 흐름

Redis를 활용한 좌석·예매 도메인의 동시 요청 제어 흐름에 참여했습니다.

4. 주요 기능

공연·좌석 예매

공연을 조회하고 좌석을 선점해 예매를 진행하는 흐름을 제공합니다.

결제 확정

PG 결제 결과를 검증한 뒤 예매 상태를 확정합니다.

쿠폰 선점·복구

결제 대기 중 쿠폰을 선점하고 실패·취소 시 사용 가능 상태로 복구합니다.

실시간 알림

예매 흐름에서 발생하는 상태 변경을 사용자에게 전달합니다.

5. 문제를 해결한 과정

웹훅 서명과 결제 금액 이중 검증

문제가 된 부분

공개된 웹훅 주소에 위조 요청이 들어오면 주문 상태가 잘못 바뀔 수 있었습니다.

해결한 방법

HandlerInterceptor에서 서명을 먼저 확인하고 주문 금액과 PG 결제 금액을 다시 비교했습니다.

확인한 결과

서명이나 금액이 다른 요청은 주문 처리 로직에 들어오기 전에 차단됩니다.

쿠폰 상태 전이 재설계

문제가 된 부분

주문과 동시에 USED 처리하면 결제가 실패했을 때 쿠폰이 돌아오지 않고, 결제 대기 중 중복 사용 가능성도 있었습니다.

해결한 방법

주문 생성 시 HOLD, 결제 완료 시 USED, 실패·취소 시 AVAILABLE로 바꾸도록 했습니다.

확인한 결과

결제가 실패해도 쿠폰을 다시 쓸 수 있고, 결제 대기 중에는 같은 쿠폰을 중복으로 사용할 수 없습니다.

6. 결과 및 회고

2단계 검증

웹훅 서명과 PG 결제 금액을 비즈니스 로직 전후로 검증했습니다.

3단계 상태

HOLD · USED · AVAILABLE로 쿠폰의 선점과 복구를 표현했습니다.

쿠폰을 사용·미사용 두 상태로만 두면 결제 중인 상태를 정확하게 표현하기 어렵다는 것을 알게 됐습니다. HOLD 상태를 추가하니 결제 실패와 취소 이후의 복구 흐름도 명확해졌습니다. 웹훅 검증은 주문 로직과 분리해 각 코드가 맡는 역할도 단순하게 유지했습니다.
